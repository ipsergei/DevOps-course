## CI/CD в проекте

**CI (Continuous Integration)** — автоматическая проверка изменений. После отправки изменений или создания Pull Request запускаются тесты, которые проверяют работу приложения, например создание заявки.

**Continuous Delivery** — после успешных тестов собирается Docker-образ. Проверенная версия готова к выпуску, но решение о развёртывании принимает человек.

**Continuous Deployment** — после успешных проверок приложение автоматически развёртывается без ручного подтверждения.

В нашей КТ автоматизируем тесты и сборку Docker-образа. Автоматического развёртывания приложения здесь нет.

## Схема работы с ветками

```text
Рабочая ветка kt3
       |
       v
   Pull Request
       |
       v
Автоматические тесты
       |
       v
  Проверка и сборка
       |
       v
      main
```

Сначала изменения делаются в отдельной ветке `kt3`, затем создаётся Pull Request в `main`. После проверки изменений преподавателем ветку можно объединить с `main`.

## Почему выбрана простая схема

Для этой работы достаточно одной рабочей ветки и `main`.

Git-flow использует дополнительные ветки `develop`, `release` и `hotfix`. Такая схема может быть полезна в больших проектах с отдельными релизами, но для небольшой учебной работы она только усложнит процесс.

Поэтому здесь удобнее использовать короткую ветку, Pull Request и автоматические проверки.

## Ожидал

Простая схема позволит выполнять задания отдельно от `main` и проверять изменения перед объединением веток.

## Ответ на вопрос из задания

Сборка Docker-образа не является автоматическим deployment. Сборка только создаёт образ, а для развёртывания нужно ещё запустить приложение в целевом окружении.
